## Codebase Patterns

- **A new `test/*.sh` is a gate only in THREE lists** (already in CLAUDE.md, restating
  because this tasklist hit it): `.chief/verify.sh`'s `CHIEF_BYSTANDER_TESTS`,
  `test/all.sh`'s `BASH_SUITE`, and `.github/workflows/ci.yml`.
- **`usage()` in `bin/chief` is the repo's longest function (192 lines on main) and it
  therefore OWNS `function_length_max`.** The ratchet's tolerance is 15 lines, so a
  usage entry longer than ~14 lines blocks the merge on its own — and the next story
  on the same branch measures against the SAME base, so every usage edit on a branch
  shares one 15-line budget. Write the entry compact the first time.
- **A `gh run list` fake is enough to test a CI probe hermetically.** Two calls are all
  `engine/cigate.sh` makes (`run list`, `run view --json jobs`); a ~15-line fake `gh` on
  PATH serving fixture JSON keyed by `--repo <slug>` covers every case, and a missing
  fixture exits 1, which is exactly what an offline/unauthenticated `gh` does.
- **Narrowing `PATH` to `/usr/bin:/bin` to simulate "tool absent" is a trap** — it also
  drops tools the code legitimately needs, so the test can pass for the wrong reason.
  Build a dir of symlinks to everything the code needs EXCEPT the one tool under test.

## US-1 — A declared gate that never ran is reported, not assumed  (2026-08-26)

Added `engine/cigate.sh` and the `chief cigate` subcommand.

Files: `engine/cigate.sh` (new), `test/cigate.sh` (new), `bin/chief` (usage entry,
`cmd_cigate`, dispatch arm), `.chief/verify.sh` + `test/all.sh` +
`.github/workflows/ci.yml` (register the test), `README.md` (command-table row +
version), `ROADMAP.md` (version), `VERSION` 0.9.2 -> 0.9.3.

What it does: for each `.github/workflows/*.yml|*.yaml` a repo DECLARES, it reports the
state of that workflow's most recent run — `RAN AND PASSED` / `RAN AND FAILED` /
`DID NOT RUN` / `UNKNOWN` / `NO GATE DECLARED`. `DID NOT RUN` covers three shapes: no
run ever recorded, a run that completed without executing a single step, and a green
run that never covered the commit asked about (`--head` / `--sha`).

**The measurement that made the "failed to start" case checkable.** A billing-blocked
run completes in ~4s with jobs present, `conclusion: failure`, and `steps: []` on every
job (cuneiform run 32944778403). A run that really executed has a populated `steps`
array (pinakes run 32827758461: 10). So "at least one step recorded anywhere in the
run" is the discriminator, and it is measured, not inferred from the conclusion string.

**A real bug the counterfactual caught.** Matching a declared workflow to its runs by
`name:` alone LOSES exactly the case this module exists for: when GitHub cannot parse
the workflow file at that ref it reports the run under `.github/workflows/ci.yml`
rather than the declared `name: ci` — so chief's own dead gate read as "no run ever
recorded" instead of "never started". The matcher accepts the declared name OR the
file path.

Observed on the real portfolio: cuneiform 11/11 DID NOT RUN, vita 1/1 DID NOT RUN,
chief 1/1 DID NOT RUN, praxis RAN AND PASSED, pinakes 3 passed / 2 failed / 1 never
run. That reproduces the 2026-08-25 measurement in the tasklist description.

Gates: `test/cigate.sh` PASS, `smoke` PASS, `ratelimit` PASS, `noworkguard` PASS,
`version-bump` PASS, `doc-sync` PASS, `bash -n` clean, doc-links 0 dead vs 0 on main,
quality ratchet OK (`function_length_max` 192 -> 200, tol 15). `shellcheck` is not
installed on this host — CI enforces it.

### Learnings for future iterations

- The state vocabulary is already stated once, in `engine/cigate.sh`'s
  `CIGATE_PASSED/FAILED/DEAD/UNKNOWN/NONE` + `cigate_label`. **US-3 must reuse those,
  not invent a second set** — that is most of its first acceptance criterion.
- `cigate_scan REPO [SHA]` is the one entry point; it already takes the commit the
  verdict is about, which is what US-3's merge record needs.
- `cigate_workflow_name FILE` is textual (`sed`, no YAML dependency) and returns the
  path when the file declares no `name:` — US-2's trigger check should extend that same
  textual reader rather than add a parser.
- `cigate_classify` is a PURE function of (slug, one run record, sha) apart from the
  jobs probe, which is why the fixtures can drive every branch of it.

## US-2 — The trigger mismatch is detectable, because it is invisible otherwise  (2026-08-26)

Extended `engine/cigate.sh` with the OFFLINE, TEXTUAL trigger check and laid it over
every arm of the scan.

Files: `engine/cigate.sh` (new `--- the TRIGGER MISMATCH ---` section + `cigate_row`,
`cigate_scan`/`cigate_unknown_rows` routed through it, `cigate_summary` counts it),
`test/cigate.sh` (the counterfactual + 11 `on:`-form fixtures), `test/fixtures/
vita-ci-2026-08-25.yml` (new — vita's workflow byte for byte), `bin/chief` (usage),
`README.md` (command row + version), `ROADMAP.md` (version), `VERSION` 0.9.3 -> 0.9.4.

What it does: reads a workflow's `on:` mapping textually (`cigate_on_block` — one awk,
no YAML dependency, no network) and asks whether a push of the repo's declared base
branch would start it. If not, the row is `DID NOT RUN` with the reason in the
operator's terms — what the workflow waits for, and what chief actually does — and
whatever GitHub said is kept alongside rather than thrown away.

**A MISMATCH WINS over a green run.** A passing run on a `pull_request`-only workflow
means someone opened a PR by hand; chief's merge was still ungated. That reassuring
surface is the exact thing this tasklist exists to stop trusting, so the row stays
`DID NOT RUN` and names the passing run in the aside.

**The mismatch is reported in the UNKNOWN arms too.** No remote / no `gh` / no network
still yields a real verdict here, because the finding is measured from the FILE. That
is the case worth having: a repo where nothing else could be measured.

**`gh` cannot answer this question at all.** "No runs" is what a dead gate and a
brand-new gate both look like; only the trigger says which. That is why US-1's network
probe left vita indistinguishable from a repo that had just added CI.

Counterfactual (real portfolio, 2026-08-26): vita 1/1 mismatch — `pull_request` +
`workflow_dispatch`, exactly the shape tasklist `72` merged against. Eight more the
billing story would have hidden: cuneiform 3 (two cron-only nightlies, one tags-only
release), talos 3, pinakes 2. praxis 0.

Gates: `test/cigate.sh` PASS, smoke PASS, ratelimit PASS, noworkguard PASS,
version-bump PASS, doc-sync PASS, `bash -n` clean, doc-links 0 dead, quality ratchet OK
(`function_length_max` 192 -> 204, tol 15). `shellcheck` not installed on this host.

### Learnings for future iterations

- **`function_length_max` headroom on this branch is now 3 LINES** (192 on main, 204
  here, tolerance 15). `usage()` in `bin/chief` owns the metric, so US-3's usage edit
  must add at most 3 lines — or move a block out of `usage()` to buy room.
- **The nogh-PATH arm of `test/cigate.sh` is a DEPENDENCY GATE, and it works.** It
  symlinks only the tools the module needs (`basename git sed head awk jq cut`), so
  reaching for `tr` or `grep` fails the test immediately. Both of mine did; both were
  replaced with `awk` and bash parameter expansion. Do not "fix" that by widening the
  symlink list — the narrowness is the check.
- **The shell this agent's Bash tool runs is `zsh`, not bash.** Unquoted `$var` does
  NOT word-split there, so a `for x in $list` loop silently iterates once and a shell
  test of engine code passes or fails for the wrong reason. Always drive engine
  functions with `bash -c '...'` or `bash <<'SH'`, never a bare tool invocation.
- **`case` globs cross `/` and GitHub's `*` does not** (`**` does). `cigate_branch_matches`
  therefore matches slightly MORE than GitHub would, on purpose: reporting a live gate
  as dead costs an operator's attention, and only the other direction is silent. Every
  ambiguous call in this module errs the same way.
- **A `schedule`-only nightly is reported as a mismatch, and that is a judgement call
  worth revisiting.** It is literally true (chief's merge never starts it) and the
  prose says "a cron clock rather than your change" — but a nightly is not usually
  meant to be a merge gate, so it is arguably noise. If US-3 or a successor wants to
  separate "cannot be started by chief" from "not intended as a merge gate", the seam
  is `cigate_event_prose` + the `CIGATE_MISMATCH_TAG` count in `cigate_summary`.
- **`CIGATE_MISMATCH_TAG` is the marker that lets a report find this finding again**
  without a fifth TSV column. It is written in exactly ONE place (`cigate_row`) and
  matched with `index($4, t) == 1`. US-3's merge record should key off the same tag
  rather than re-matching the prose.
