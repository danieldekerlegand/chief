### Learnings for future iterations

- **Where a verdict may NOT live: the tasklist JSON.** Two independent failures. (1)
  `run_worker`'s isolation guard runs `git checkout -- "$TASKS_REL/$name.json"` in the
  PROJECT checkout on every iteration — an uncommitted field there is silently
  discarded before the decision arm ever reads it. (2) Committing it on the base is
  worse: the branch waiting on the decision has almost always committed its own edit to
  that same file (the pass-flags), so the verdict commit collides at rebase and ends the
  decided tasklist in REBASE-CONFLICT. Gitignored state under `$STATE_ROOT` is invisible
  to both — the same rule CLAUDE.md already states for pause/research/snapshot files.
- **The driver reads `$SRC`/state, never the worktree copy, for anything an operator
  authored.** The worktree's `tasks/…` and `.chief/state/prd.json` are both writable by
  the agent; `test/decision-agent.sh` exists precisely because an agent will write a
  `.verdict` if you let it count.
- **Bind an approval by a PROJECTION, not by bytes.** `passes`/`notes` differ between
  the copy an operator decided from and the copy about to merge, so a raw-bytes checksum
  never matches once. `{id,title,acceptanceCriteria}` is what a human said yes to.
  (`decision_stories_id`, mirroring `review_plan_id`.)
- **`worker_park`'s `!!` line goes to `$STATE/parallel/<name>.log`, not to the run's
  stdout** — the scheduler summary carries only the status line. A test asserting on a
  park's REASON has to read the per-tasklist log.
- **A test fixture built from a live `tasks/chief/*.json` rots the day that tasklist
  retires**, and rots SILENTLY: `jq` on a missing file writes an empty target, and the
  assertions then pass/fail for reasons unrelated to what they claim to test. Build
  fixtures with `jq -n`.
- shellcheck could not be installed on this host (homebrew permission failure), so only
  `bash -n` was run locally; CI enforces `shellcheck -S error`.

### Learnings for future iterations

- **`chief decide` leaving the tasklist DIRTY meant the next run never started.** The run's
  startup guard ("uncommitted tracked changes on 'main' — commit or stash them") fires
  before anything is scheduled, so US-1's flow only worked in its test because the stale
  step happened to `git commit -am` in between. Any operator command that edits a tasklist
  must commit it (`chief retire` already did — same shape, `--no-commit` escape) or write
  nothing at all.
- **Where a verdict may live, refined: a tasklist file may carry it only if that file will
  never be REBASED again.** `--retire`/`--decline` end the tasklist on the spot, so their
  JSON is safe and is the human-readable copy. `--proceed`/`--unpark` leave it live and its
  branch is about to replay onto this base, editing that same file — so they write NOTHING
  to it (an `--unpark` of an unparked tasklist writes no bytes at all, deliberately, because
  a dirty tree is the failure above), and `finalize_merged` stamps the verdict onto the
  `completed/` record instead. That record is written once, after the last rebase.
- **AUTHORITY belongs to the flag, never to the verdict word.** "postgres", "approved",
  "the MIT row" are the operator's vocabulary; chief has no dictionary that could tell a
  yes from a no in it. One mapping (`decision_authority`), two call sites — the writer
  asserts against it, the reader derives from it.
- **A new terminal state is FIVE driver edits plus two viewers**, and missing one is how an
  outcome gets mis-classified (this whole tasklist's family): `worker_park` arm, `reap`
  status→state, `tasklist_outcome` (BOTH halves — the status arm and the get_state
  fallback), the summary `case`, the headless `hl_*` bucket, then `monitor.sh`'s glyph and
  `STALE_QUIET_PHASES`. `dep_broken` is a sixth, and a real decision: `decision-declined`
  is in it because the work its dependents wait on is never arriving.
- The ratchet's `single_use_functions` is AT tolerance (+2 of 2) on this branch. US-3 has
  no room for a new single-call helper without deleting one.

## Post-story fix — the merge gate's flake in test/merge-batch.sh PART C
Wed Aug 26 2026

Every story on this branch was already `passes:true`, but the merge-time
`.chief/verify.sh` had come back RED and left a `⚠️ PRIOR VERIFICATION FAILED` block at
the top of this log. The single failure was NOT in this tasklist's code:

    merge-batch| MERGE-BATCH FAIL: PART C: expected 2 verifications
                 (1 batch tip for 2 + 1 floor for charlie), got 1
    BYSTANDER FAIL: test/merge-batch.sh failed

It is a pre-existing FLAKE in the test, not a regression from 116 — `test/merge-batch.sh`
passes on this branch unmodified about half the time, and every other file the branch
touches is unrelated to the merge queue.

Root cause, reproduced 2/2 in an isolated PART C harness. `charlie` is the branch in a
`review` overlap zone, so it is excluded from batching and takes the serialized floor.
Its floor gate is served from the verify CACHE whenever it reaches the merge lock before
its peers land — its own log says so:

    >> charlie: chief/charlie is strictly ahead of main — rebase is a no-op, skipping it
    >> verifying chief/charlie (rebased)
    >> verify SKIPPED: tree 52e9018… (GREEN verdict from …/verify-cache/…; same base and verify hook)

That is US-4's designed behaviour ("the agent verify and merge gate are not duplicated"):
the agent boundary already ran the gate on that exact tree/base and recorded it, so a
merge input that did not move reuses the verdict. The gate WAS paid — inside the
worktree — but the fixture's counter is keyed by `basename "$PWD"`, so an agent-boundary
run lands in `charlie.verifies` and only merge-phase runs land in `zoned.verifies`.
Whether charlie or its peers reach the lock first is a race, so the count was 2 or 1.

PART A already anticipates exactly this and accepts `2|3` with a comment; PART C was
missed when US-4 landed.

Files:
- `test/merge-batch.sh` — PART C now asserts BOTH readings instead of one: charlie's own
  log must show `>> verifying chief/charlie` (it took the floor's gate step — the claim
  the part exists for), and then the counter is pinned to the reading that log reports —
  1 when `verify SKIPPED` is present, 2 when it is not. Also documents that the counter's
  cwd-basename key is load-bearing, not incidental: it is what keeps every other part's
  number counting merge-phase gate runs only.

No engine change, so no `VERSION` bump (test/version-bump.sh gates `bin/`/`engine/`/
`scripts/`/`install.sh` only) and README/ROADMAP stay at v0.9.8.

### Learnings for future iterations

- **A verify-count assertion in a parallel test is racy the moment the verify CACHE can
  serve it.** `verify_cache_try` (engine/lib.sh) hits when tree + base + hook are all
  unchanged, which for the FIRST branch to reach the merge lock is the normal case —
  its rebase is a no-op. Any test asserting "N gate runs for N tasklists" has to say
  which reading it got, and the branch's own log is the witness (`verify SKIPPED …` vs a
  fresh hook run). Prefer pinning the count to the log over widening it to a range: a
  bare range also passes when the floor was never reached at all.
- **The gate is paid in two different CWDs.** Merge-phase verify runs at the repo root
  (`run_verify "$work_repo"`); the agent boundary runs the SAME hook with cwd = the
  worktree (`_agent_verify_final` → `run_verify "$CHIEF_PROJECT"`). A fixture hook that
  keys anything off `$PWD` therefore partitions the two, which is useful — but it means
  "the gate did not run" and "the gate ran somewhere this counter cannot see" look
  identical. Say which one you mean.
- **A red merge gate is not always this branch's fault.** Check whether the failing test
  passes on the branch unmodified before changing engine code: here it did, ~50% of the
  time, and the fix belonged in the test rather than in anything 116 shipped.
- **The driver RE-SEEDS `.chief/state/progress.txt` at run start**, replacing it with a
  fresh header plus the `⚠️ PRIOR VERIFICATION FAILED` block. Since this repo TRACKS that
  file, committing it as-found deletes every earlier note from the tree. Restore
  `git show HEAD:.chief/state/progress.txt` first, then append — the log is append-only
  by contract, and the driver's re-seed does not know that.

## US-2 — A recording path the agent can actually use
Wed Sep  2 2026

US-1 taught `_agent_verify_final` to READ the verdict cache. Nothing an agent could
run WROTE to it: `.chief/verify.sh` invoked from inside a turn is a plain shell
command chief never sees, so the ~20-minute suite run bought nothing and both later
gates were still paid in full. `chief verify` is the mechanism that replaces the prose
instruction ("never run the full workspace suite inside a chief iteration") that had
already failed three times in one day in one repo.

Files:
- `bin/chief` — `cmd_verify` (+ dispatch arm + `usage()` entry). Runs the SAME hook the
  same way (`run_verify "$CHIEF_PROJECT" "$CHIEF_TASKLIST"`, so a tasklist's own
  `"verify"` array is honoured), exits with the hook's status, then
  `verify_cache_record`s it. Inside a turn it needs no arguments — the driver has
  already exported the worktree, the run's `$STATE`, the tasklist and the work base,
  and those are PREFERRED over `.chief/config` (a `repo:<sub>` tasklist's base is not
  the one the config names). `--no-record` runs the gate and writes nothing.
- `engine/instructions.md` — step 5 of the turn prompt. This is the surface that
  matters: the whole story exists because prose in a project CLAUDE.md did not reach
  the agent at the moment it decided to run the suite.
- `docs/reference/verify-hook.md` — "Running this gate yourself: `chief verify`".
- `README.md` command table (doc-sync gates it), `CLAUDE.md` (CLI list + a line in the
  quality-gates section), `VERSION` 0.9.9 → 0.9.10 with both bold version claims.
- Drive-by: two UNESCAPED backticks inside unquoted heredocs — `bin/chief`'s
  `usage()` (`` `chief run` ``) and `engine/quality.sh`'s `qq_usage` (`` `ratchet
  --help` ``). Both were live command substitutions; `chief help` literally STARTED A
  RUN. CLAUDE.md documents this exact hazard and the file had regressed into it twice.

### Learnings for future iterations

- **The refusal is the design, not a safety net bolted on.** The cache key is HEAD's
  TREE; the hook tests the WORKING tree. Recording while those differ is the one
  failure mode of this whole mechanism that could merge a red tree, so a dirty tree
  (tracked OR untracked) records nothing, and neither does a run HEAD moved under.
  Both still RUN the gate and still return its status — refusing to RECORD is never
  refusing to CHECK. The agent-facing consequence is an ORDER: commit, then
  `chief verify`, then `--amend` if it comes back red.
- **`chief verify` deliberately never READS the cache.** `verify_cache_try` keys on
  HEAD's tree alone and says nothing about uncommitted work, so a green record plus an
  edit made since would answer "green" about code nothing had run. The agent boundary
  and the merge gate can read it precisely because their trees are committed and
  still; this caller's tree is the one that is expected to be moving.
- **A `chief` subcommand run from inside an agent turn INHERITS the run's environment**,
  and that is load-bearing, not incidental: `CHIEF_VERIFY_CACHE_STATE`,
  `CHIEF_PROJECT`, `CHIEF_TASKLIST`, `CHIEF_VERIFY_{HOOK,BASE,TASKS_DIR,REPO}` are all
  exported by driver.sh at `driver.sh:2599`. It also means any SCRATCH-REPO test of
  such a command must `env -u` all of them: the first two attempts at this story's
  fixture silently ran chief's own 20-minute gate against the WORKTREE instead of the
  temp repo, because `load_project`'s answer was being overridden by the outer run's.
- **`awk '/^name\(\)/,/^EOF$/' file | grep -n '[^\\]`'` is the check CLAUDE.md asks
  for, and it finds real bugs** — run it over `bin/chief` and every `engine/*.sh` after
  touching any usage text. `bash -n` is clean on a live command substitution and no
  test renders `--help`, so nothing else catches it.

    reflog|  @{14} commit: chore(chief): alpha complete @f19d300 — record + retire
    reflog|  @{13} checkout: moving from chief/alpha to main

There is no `chief/alpha -> main` entry between @{15} and @{14}: the merge phase's
`work_checkout "$work_repo" "$work_base"` **failed and was ignored** (its output is
`>/dev/null 2>&1` and its return value was unused). HEAD stayed on the branch, so
`git merge --no-ff chief/alpha` merged the branch into itself — `Already up to date.`,
**exit 0** — and the site read that as success: status `MERGED @<branch tip>`,
`finalize_merged` writing the completed record + retire commit onto **chief/alpha**
(@{14}), main never moving, `completed/` never getting a record, and the run summary
printing `alpha  done  [MERGED @e4619e0]`. @{13} is the EXIT trap's identical checkout
landing first time seconds later — which is what makes the cause transient.

Confirmed the mechanism deterministically in a scratch repo: with `.git/index.lock`
held, `git checkout main` exits **128** and HEAD does not move; `git merge --no-ff feat`
then prints `Already up to date.` and exits **0**. The contention is real — the project
index is SHARED, and the reconcile step's isolation guard (`git checkout -- tasks/…`)
and `finalize_merged`'s `rm`/`add`/`commit` both mutate it, which is why both already
take `idx_lock`. `work_checkout` never did.

- **A git command whose no-op case exits 0 needs its PRECONDITION checked, not its own

- **A fix to a stall flag is not finished until the flag has been shown to still

## Verification recovery — test/verify-stream.sh PART D/E were RACY under load

The branch came back from the merge gate red on `test/verify-stream.sh` PART D
("the record was NOT bumped by the gate's own output") with all three stories
already passing. The engine was NOT at fault — the flake is in the probe.

WHAT REPRODUCES IT. Standalone the file is green every time; that is why it passed
in US-2's and US-3's own runs and failed under `test/bystander.sh`, which runs it
as 1 of 58. Six concurrent runs of the file: 2 failed, in two different places —
PART D on `HB_TICKED=0`, and PART E with the row rendering
`↳ agent-turn for 40m · iter 1 · 0s ago`, i.e. a heartbeat that was never aged.

THE CAUSE, one race with two faces. `_verify_tick` PRINTS a line and THEN writes
the record, so at the instant a marker reaches the log that `live_set` is still in
flight, and `phase_probe` sampled once on each side of it:

  - `backdate` (live_get + sed + mv) races that write. The tick lands after the
    `sed` and restores `heartbeat` to `now`, so the baseline `hb_before` is `now`
    and the second line cannot beat it by 100 -> PART D. In PART E the same
    clobber leaves a fresh heartbeat at 40m, so no stall flag -> the reproduction
    stops reproducing. (Quieter variant: a tick between backdate's own `live_get`
    and its `sed` leaves the pattern unmatched, and a no-op backdate looks exactly
    like a successful one.)
  - `hb_after` was read the moment `MARK_SECOND` hit the log — before the bump —
    so a working ticker reads as a dead one.

PART F already had both right and said so ("The marker reaching the LOG is not the
tick"), and established quiescence by hand before its own backdate. D and E did
not. The fix factors F's discipline into two helpers so the parts cannot drift:
`backdate_settled` (re-assert until a read-back comes back aged — bounded, because
every call site is a point where the hook is BLOCKED on a release file, so at most
one tick is in flight) and `await_tick` (poll for the bump past a floor instead of
sampling once). Test-only change; no engine edit, so VERSION stays 0.9.15.

— that is the reproduction, run before the fix, and it is the mutation check.
After: 16 of 16 concurrent runs green, plus standalone green at ~20s wall.
test/stall-flag.sh PASS, test/liveliness.sh PASS, test/verify-cache.sh PASS,

### Learnings for future iterations

- **A test that samples a record around a marker in the log is racy by
  construction.** Everywhere in this engine the pattern is *emit the bytes, then
  write the record* — `_verify_tick` does it, and it is the right order (the
  record is stamped for output that has actually left). So the log marker is
  strictly EARLIER than the state change it implies. Never read the record on the
  strength of having grepped the log: **poll the record**. Write the assertion as
  "wait until the value moves past X, with a deadline", never as "read it once".
- **An external write to a liveliness record must be CONFIRMED, not issued.**

- **When the merge gate comes back red with every story passing, suspect the test
  before the engine** — but prove it: reproduce the failure first, on the unfixed

## 120/US-1 — A recorded verdict is reused whatever its status
Thu Sep  3 2026

The verify cache reused a GREEN verdict and re-earned a RED one, so an agent that
could not fix a gate paid the entire gate again on every iteration to be told the
same thing (cuneiform 2026-09-03: `388-the-panel-emission-contract` ran 01:55→07:52,

Files:
- `engine/lib.sh` — `verify_cache_try` honours ANY recorded status and RETURNS the
  recorded exit status on a hit, 1 on a miss, with `$VERIFY_CACHE_HIT` /
  `$VERIFY_CACHE_STATUS` / `$VERIFY_CACHE_RECORD` set on every call. New

- `test/verify-cache.sh` — PART D inverted to the new contract (reuse + replay + still

- `VERSION` 0.9.15 → 0.9.17, README + ROADMAP bold version with it.

### The key grew a FOURTH component, and that is the real find here

Reusing a red exposed a latent unsoundness in `tree.base.hook`. A project worktree
never initializes its submodules, so the AGENT BOUNDARY runs the hook with `dep/` an
empty directory; the MERGE PHASE runs `submodules_sync` first (93) and runs the same
hook, over the same tree, against a submodule checked out to match the gitlink. Same
tree sha, same base, same hook — a different filesystem, and CHIEF ITSELF is what
moved it. `test/submodule-gitlink.sh` is exactly that gate: with three parts it read
the boundary's legitimate red ("submodule working tree is STALE") back at the merge
and never re-ran the check `93` exists to guarantee, ending a mergeable tasklist
VERIFY-FAILED three attempts running.

The same hole exists for GREEN and pre-dates this tasklist (it arrived with 117's
boundary read) — a boundary green taken over a stale submodule tree could be reused at
merge, which is the direction that MERGES something unchecked. Nothing had noticed
because a green boundary verify over an empty `dep/` is rare; a red one is not.
`verify_cache_subs` (a cksum of `git submodule status --recursive`, `nosub` where
there are none) closes both.

### Learnings for future iterations

- **A HIT/MISS predicate that also carries a status must fail in the SAFE direction.**
  `verify_cache_try` cannot signal both from its return alone (miss and red hit are
  both non-zero), so the choice is which confusion a careless caller makes. Returning
  the RECORDED STATUS means a caller that ignores `$VERIFY_CACHE_HIT` re-runs a red
  hit — wasteful, never wrong. The inverse (0 = hit) would make the same oversight
  skip the gate and accept a failing tree.
- **`verify_cache_record` reads its output file TWICE** (line count, then tail), so a
  process substitution silently records nothing on the second read. The `-` stdin mode
  exists for callers that already hold the output in a variable.
- **The FAKE PROVIDER in test/verify-cache.sh must commit at most ONCE per
  `run_agent`.** A red gate refuses the completion, so the loop takes another turn; a
  provider that commits every turn never stops making progress and runs to the hard
  iteration ceiling (observed: 20 iterations, 24 hook runs). It now skips the commit
  when its token is already in `product.txt`.
- **A verdict cache key must name every input the gate READS, not every input the
  COMMIT names.** The tree sha describes the repository's content; the hook runs
  against a FILESYSTEM, and for a superproject those differ by exactly the submodule
  checkout — which chief moves between its own two reads. Anything else chief mutates
  between a record and its reuse belongs in the key on the same argument.
- **`run_worker` (driver.sh) is the `function_length_max` ceiling.** It measured
  596 → 616 raw lines; a 12-line addition put the ratchet at +14 against a tolerance
  of 15. Condensing the arm to 11 lines and moving the scratch-file handling into
  `verify_cache_record` brought it to +6. Any story touching that function should
  check `bash engine/quality.sh ratchet` before it is happy.
- **A follow-up commit touching `engine/` re-stales `VERSION`,** exactly as CLAUDE.md
  says. The submodule-key fix landed as its own commit and `chief verify` blocked on
  VERSION-BUMP before running a single test; 0.9.16 -> 0.9.17 plus both bold README /
  ROADMAP versions cleared it.
- **`test/ratelimit.sh` can fail inside the bystander block under host load** while
  passing 3/3 standalone. Observed once here: its run reached `● rl finished →
  MERGED @29dc2e0` and was then TERMed, with load average 5.65 and two other repos'
  chief runs live on the machine. Re-run it standalone before believing a bystander
  ratelimit failure.
- **Two tests anchor `sed` patches on lines in `_agent_verify_final`, and this story
  moved one of them.** `test/verify-stream.sh` PART C restores the pre-119
  command-substitution form; its anchor was the `run_verify … | _verify_tick` line,
  now `… | tee "$vlog" | _verify_tick`. It failed with "its anchor moved. Fix this
  patch, do not delete the reproduction" — which is the right failure, and the right
  response is to re-anchor it. `test/verify-cache.sh` PART E patches
  `if verify_cache_try ` in the same function and still applies. Grep both before
  touching that function.
- **`chief verify` IS the escape hatch until US-2 ships one.** It never reads the
  cache and always records, so a red verdict cached over a flaky gate can be cleared

## 120/US-2 — The operator can force a re-run
Thu Sep  3 2026

US-1 made a RED verdict reusable. That is only safe if the operator can DISBELIEVE

- `docs/reference/verify-hook.md` — "Forcing a re-run: `CHIEF_VERIFY_CACHE=0`", in

### Learnings for future iterations

- **A test harness that always SETS a toggle cannot fail when the toggle's DEFAULT
  is wrong.** `run_agent` passed `CHIEF_VERIFY_CACHE="${VC_HATCH:-1}"`, so flipping
  the engine's default to "cache off" (`${CHIEF_VERIFY_CACHE:-0}`) passed all seven

- **A bypass is not an override.** The hatch had to REPLACE the record, not just

  PART F plants a sentinel line in the record and fails if it survives.
- **Check an escape hatch AFTER locating what it overrides.** Putting the test at
  the top of `verify_cache_try` is one line cheaper and produces a log a person
  cannot act on — an ordinary miss and a forced re-run read identically. Locating
  the record first lets the line name it.
- **A red bystander block under load is worth one standalone re-run before it is

## Verification recovery — the stranded base repo names what defeated it (2026-09-04)

The run resumed with all three stories `passes:true` and a
`⚠️ PRIOR VERIFICATION FAILED` block naming ONE failure: `test/dirty-checkout.sh`,
in section C (SIGKILL mid-merge). Not caused by this tasklist — nothing in the
verify cache touches it — but a real engine defect, not a flake to wave through.

WHAT THE LOG SHOWED, and why it was undiagnosable:

    (auto-recover: base repo stranded on 'chief/dc-kill' from a crashed run — restoring 'main')
    ERROR: could not restore 'main' from 'chief/dc-kill' — resolve by hand.

Two lines, no cause. The test dumps 40 lines of run log and 60 of worker log and
neither holds one, because EVERY command in that arm discards its error
(`rebase --abort`/`merge --abort`/`add`/`commit` are all `|| true`, and the
checkout was `>/dev/null 2>&1`).

THE MECHANISM (established, not guessed). C waits for `stash=` to appear in the
`.critical` marker and then SIGKILLs the process group. What runs immediately
after that marker write is `sweep_worktree` → `remove_worktree` →
`work_checkout_or_stop "$work_repo" "$branch"` → `merge-base` → `rebase` — i.e.
a dense run of INDEX WRITERS in the base repo. A kill landing inside the
checkout leaves `.git/index.lock` behind, and that lock is released by nobody.
Verified directly: with a stale `index.lock`, `git checkout main` dies rc 128
with "Unable to create '.git/index.lock': File exists … a git process may have
crashed in this repository earlier: remove the file manually to continue" — the
one message that says which file to remove, and the one the arm threw away.
Load widens the window (16.58 on 14 cores in the failed run), which is why it
reads as a load flake; it passed 5/5 standalone here.

Probing notes, for whoever chases the next one of these: copy the test to /tmp,
replace its `trap 'rm -rf "$WORK"'` and PIN `ROOT` to the real repo (it is
derived from `BASH_SOURCE`, so a copy elsewhere fails at the awk-lift of
`merge_stash_push`). Inserting a `sleep` before the kill does NOT reproduce this
— it makes the merge phase get FURTHER, past the critical section, so the stash
pops normally and a different assertion fails. That is a rigged failure, not the
one in the log; the tell is `HEAD=main` in the probe instead of
`HEAD=chief/dc-kill`.

THE FIX (engine/driver.sh):
- `work_checkout` retains the LAST failed attempt's output in `$WORK_CHECKOUT_OUT`
  rather than sending it to `/dev/null`. The happy path is unchanged — a
  successful checkout's chatter is still never shown.
- `work_checkout_cause INDENT` prints it (two call sites, so it does not trip
  `single_use_functions`), and always returns 0: both callers are on their way
  to their own exit status and neither may be diverted by an empty answer.
- The auto-recover checkout now GOES THROUGH `work_checkout`. It was the last
  bare `git checkout` on a path that has a guarded form — the same asymmetry
  `work_checkout_or_stop` was created to close at the merge site, and CLAUDE.md
  already states the rule ("work_checkout, never a bare `git checkout`").
  Retries also make the merely-transient case self-clearing.
- `work_checkout_or_stop`'s "(retried)" message names the cause too — it had the
  same silence at the merge site.

WHAT I DELIBERATELY DID NOT DO: auto-delete the stale lock. The arm holds the
driver lock, so no chief run is live in that repo — but a NON-chief git process
(an operator's editor, a `git commit` in another terminal) can hold `index.lock`
legitimately, and `index.lock` carries no pid, so staleness is not decidable from
the file. Age is the only available discriminator and a large checkout can hold
the lock for a long time legitimately. Deleting a live lock corrupts someone's
in-flight git operation; telling them precisely what to remove costs one command
in a rare crash path. If a future tasklist wants the automatic clear, that is the
tradeoff to argue, and it should be argued deliberately rather than smuggled in
here.

THE TEST (test/dirty-checkout.sh, new section E). The race is not reproducible on
demand, so E pins the STATE it produces instead: strand the base on a `chief/*`
branch, plant the `index.lock` the kill leaves, assert the run REFUSES and that
the refusal names `index.lock`; assert HEAD did not move (a recovery that cannot
finish may not leave the operator worse off than the crash did); then clear the
lock and assert the arm still recovers to `main` — so E is not merely asserting a
failure. Placed AFTER D because D needs the dirty tree C hands it; E starts with
`reset --hard` and is last.

Gotcha it cost me: by section E every fixture tasklist has been retired to
`completed/`, and chief stops at "No tasklists in tasks/chief/ yet" BEFORE it
looks at the checkout — so E has to author a live tasklist first, or it asserts
on a run that never reached the gate. `CHIEF_CHECKOUT_RETRIES=0` keeps it from
paying 3×1s of retry sleep.

MUTATION-CHECKED: restoring the bare `git checkout … >/dev/null 2>&1` in the
auto-recover arm fails E with "the failed recovery did not name WHAT defeated
it". The revert had to be COMMITTED to be seen — dirty-checkout installs chief
from `git rev-parse HEAD`, so an uncommitted engine edit is invisible to it
(CLAUDE.md says this; it is easy to forget when the edit is one line).

OBSERVED: test/dirty-checkout.sh PASS, all five sections, standalone.

### Learnings for future iterations

  core count. Set an env-captured knob BEFORE the `.` — and note this test is in
  `test/all.sh` only, which is why it rotted silently: it was in neither the merge gate
  nor CI. Both lists now carry it (with `concurrency` and `gate-budget`).
- **A phase list that is only DISPLAYED becomes load-bearing the moment something
  budgets on it.** `concurrency_phase_kind` counted `merge-wait` (a worker asleep on a
  lock) and `merge-conflict` (a parked terminal state) as gates. Harmless as a number
  on `chief ps`; as an admission input it would let one run's merge queue read as N
  gates and starve every other repo on the host. Before reading an existing counter,
  check what it counts, not just what it is called.
- **Read the phase you intend to RESTORE before publishing a new one.**
  `_agent_verify_final` reads `prev_phase` to put back after the gate; the admission
  hold publishes `gate-budget-waiting`, so ordering the two the obvious way would have
  restored the hold's own phase and left it outliving the thing it described.
- **An admission control needs two independent no-deadlock floors, not one.** The
  predicate admits whenever nothing of chief's is gating (so a cleared host always
  moves), and the wait itself is time-bounded (so a live record chief cannot clear —
  a wedged gate, a stuck pid — releases anyway). Either alone is a single point of
  permanent portfolio halt.
- **`[ x ] && cmd` at the end of a `set -e` function is a returning-1 trap.** The new
  predicates use `if … then return 0; fi` instead, which is also what makes them safe
  to call from `driver.sh` and `agent.sh` (both `set -e`).
- Still open for a later story: the opt-in **merge queue** (`engine/mergequeue.sh`)
  runs its batch verify on its own path and is not yet admitted through the gate
  budget. It is off by default, so the floor is covered.

Files:
- `engine/concurrency.sh` — `CHIEF_MACHINE_LOAD_LIMIT` (+ `_REQUESTED`/`_DISABLED`,

- `test/load-admission.sh` (new, in all three gate lists) · VERSION 0.9.20 → 0.9.21

### Learnings for future iterations

- **A capacity signal chief did not cause needs a floor keyed to chief's own
  contribution, not to time alone.** Load average counts what chief cannot finish and
  cannot see, so "wait for it to fall" can wait forever while chief is idle. The bound
  that works is: defer to the load line only while a gate of chief's is in flight.
  That is the SAME zero-gates floor the gate budget already stands on, so the two
  controls share one no-deadlock argument instead of each carrying its own.
- **An early return written for one knob silently disables the next one added below
  it.** `chief_machine_gate_admit` began `if GATE_BUDGET_DISABLED; then return 0; fi`
  — correct when the gate budget was the only control, and the moment the load rule
  joined it, `CHIEF_MACHINE_GATE_BUDGET=0` turned off a knob the operator never
  touched. A short-circuit at the top of an admission function is a claim that nothing
  else will ever be asked. Mutation 3 in `test/load-admission.sh` pins it — and it did
  NOT fail on the first draft of that test, because the draft asserted on the
  PREDICATE while the bug was in the WRAPPER. **Mutate the layer you shipped, not the
  layer you find convenient to call.**
- **`chief_machine_admits KIND` instead of two near-identical predicates.** Two
  `_allows` functions differing only in which budget they consult is exactly what the
  `duplicate_blocks` ratchet counts, and it is also two places for the load check to
  later be added to one of.
- **Re-sample inside the wait loop.** A hold taken at a spike that reads the value
  once outlives the spike; `chief_machine_activity` was already refreshed per pass and
  the load was not, which would have made the freshest input the stalest one.
- **`python3 -c 'json.dump(...)'` on `.chief/state/prd.json` escapes every non-ASCII
  character** unless you pass `ensure_ascii=False`. Valid JSON, unreadable diff — the
  descriptions in this repo are full of em-dashes and middots.
- shellcheck is still not installed on this host; ran 0.11.0 via `npx --yes
  shellcheck@latest -S error` on the four changed shell files, clean.

Learnings for future iterations:
- **A red test is landed by keeping it OUT of the three gate lists.** A test that
  records a hole BEFORE the key that closes it exists cannot go in
  `.chief/verify.sh`'s `CHIEF_BYSTANDER_TESTS` / `test/all.sh`'s `BASH_SUITE` /
  `.github/workflows/ci.yml` — it would block the very branch that fixes it. Nothing
  derives one list from another and nothing enumerates `test/`, so the file is simply
  unwired; `bash -n` and `shellcheck` DO glob `test/*.sh`, so it must still be clean.
  The story that adds the key adds the file to all three in the same commit. The
  header says so, in those words, so the next reader does not take the gap for an
  oversight.
- **On macOS a cwd read back out of the process table is `/private/var/…` while
  `$TMPDIR` is `/var/…`.** `engine/reap.sh` canonicalises its scope dir first
  (`chief_reap_canon` = `cd && pwd -P`); a test that compares the literal strings
  reports "it escaped the worktree" for EVERY process in the worktree, which is a
  false PASS for a test of this shape. Compare against both spellings (`canon()` in
  `test/reap-escaped.sh`). The first draft of this test passed its own escape
  assertion for exactly the wrong reason, and the positive control is what caught it.
- **A negative assertion about a sweep needs a process the sweep DOES find.** The
  fixture spawns a sibling that STAYS in the worktree; key 1 names it and it is
  reaped in the same run, so "the escapee was not listed" can never be read as "the
  sweep never ran" or "the fixture never started". Asserted at both levels: the key
  primitive (`chief_pids_cwd_under`) and the `chief reap` report.
- **`$$` survives `exec`, which is how a fixture wears a run id that names its own
  pid** (`bash -c 'exec -a "… --chief-run=$IDBASE-$$" bash "$0" "$@"' script args…`).
  `test/reapenv.sh` stages its unregistered live driver the same way. For
  `chief_run_id_resolvable` to account for the run at all, a worktree dir named
  `<repo>-<cksum>` matching the run id's cksum field must exist under the temp
  worktree root — without it the sweep correctly REFUSES to judge the run and every
  assertion below reads as "not found" for the wrong reason.
- **Re-parenting is cheaper to stage by killing the parent than by double-forking.**
  `kill -9` the fixture driver and its child is re-parented to PID 1 within a second;
  poll `ps -o ppid=` rather than sleeping a fixed time. `trap "" TERM` in the escapee
  also pins the TERM -> KILL escalation, since the field process ignored SIGTERM too.
- The driver's own transient `sleep 1` (from `while :; do sleep 1; done`) survives its
  parent for up to a second with its cwd still in the worktree, so it shows up as an
  extra `[cwd]` orphan in the report. Harmless, but do not build an assertion on it —
  it is racy. That is what the explicit control process is for.
- **`shellcheck -S error` is RED on main, and has been since shellcheck got stricter.**
  Three findings, none of them this branch's: `engine/quality.sh:60` SC1073+SC1072 —
  a PROSE comment that begins `# shellcheck severity for the lint family.` is parsed
  as a shellcheck DIRECTIVE and fails to parse — and `engine/sweep.sh:396,404` SC2066
  (`for repo in "$current"`, which cannot word-split). CI run 33978312283 (2026-09-05)
  fails on exactly these, on BOTH jobs, byte-identical to a local run. So the next
  iteration that touches `engine/` should clear them in passing; it owes a `VERSION`
  bump anyway, which is the reason NOT to clear them from a test-only story (the bump
  would then drag `doc-sync` in behind it). Note the general trap: a comment in an
  engine file must never begin with the word `shellcheck` after the `#`.
- `brew install shellcheck` fails on this host (`/opt/homebrew` is owned by another
  user and wants a `sudo chown`). The standalone release tarball works and installs
  nothing: `curl -fsSL .../shellcheck-v0.10.0.darwin.aarch64.tar.xz | tar x` in
  `/tmp` and run the binary from there. Worth doing — `.chief/verify.sh` silently
  SKIPS shellcheck when it is absent, so a branch can be "green" locally and red in CI.
- **`git commit --amend` AFTER `chief verify` throws the verdict away.** The cache key
  is `tree.base.hook.subs`, so amending — even to add a note to `progress.txt`, with
  no `.sh` touched — changes the tree and the recorded verdict no longer applies to
  HEAD. Finish the commit (notes, tasklist flags, progress) FIRST, then verify once.
  The one saving grace is that chief's own end-of-turn run records for whatever tree
  HEAD ends on, so the merge read is still served from a cache; the cost is paying the
  ~10-minute behavioural block one extra time.
