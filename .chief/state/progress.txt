### Learnings for future iterations

- **A `PRIOR VERIFICATION FAILED` block is host state, not branch state.** The driver
  re-seeds it into a fresh `progress.txt` from `$SNAP/<name>.verify-failed.log` at the
  top of every run (`engine/driver.sh:2529`), which lives OUTSIDE the worktree. Fixing
  the failure does not clear the block — only a green merge-time verify does. So when
  every story already passes and the block is present, the correct iteration is
  *re-run `.chief/verify.sh` and record what it printed*, not go looking for more work.
- **`✗ … failed` in the behavioral log is usually a FIXTURE, not a failure.** The
  worktree-pending and stall-flag tests render synthetic `chief ps` rows, so a naive
  `grep -i fail` over the verify log reports ~26 "failures" on a fully green run.
  Match `FAIL:` / `BLOCK —` instead.
- **The ratchet is a delta gate with a narrow tolerance** (`single_use_functions` tol
  2). A branch that adds a family of small helpers will trip it even when each helper
  is reasonable — the fix that worked here was folding single-caller helpers into
  their only caller and routing duplicated arms through the existing `worker_park` /
  `pending_record`, not loosening the tolerance.
